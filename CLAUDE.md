# uk-business-mcp (Ledgerhall proxy)

FastMCP proxy that bundles `govuk-mcp`, `uk-legal-mcp`, `uk-due-diligence-mcp`,
and `property-shared` behind a single URL. Marketed as the **Ledgerhall**
product on bouch.dev.

- **GitHub:** `paulieb89/uk-business-mcp`
- **Deployed:** `https://uk-business-mcp.fly.dev/mcp`
- **Shape:** non-standard — single `server.py` at repo root, no package. `uv sync` needs `--no-install-project`.

This repo has no domain tools of its own — it only proxies upstreams via
`create_proxy()`. All tool logic lives in the upstream servers. The mounts are
live (no PyPI pin): an upstream release reaches Ledgerhall clients immediately.
For the current tool list run `uv run --no-sync fastmcp inspect server.py:mcp`
(it lists the live upstreams' tools) rather than trusting a count in prose.

## Stack and checks

- FastMCP 4.1.8 / MCP SDK 2.3.0 (same SDK line as the upstreams). Proxied
  connections identify as `ledgerhall` via `Client(client_info=...)`; the
  upstreams' `*_client_connections_total{client_name}` should show that name,
  not the SDK default `mcp`.
- `/health` returns `status`, `version`, `git_sha` (Docker build arg from
  `release.yml`) and `upstreams` — each mount's own `/health` status, version and
  git_sha, cached 60s with a 2.5s timeout per upstream. An upstream being down
  never changes the proxy's `status`: Fly would restart this machine for it.
- `docs/tool-reference.md` is generated by `scripts/gen_reference.py` (shared
  verbatim with uk-legal-mcp and uk-due-diligence-mcp) from `fastmcp inspect`;
  regenerate after an upstream release changes its surface. `release.yml` runs
  `--check`.
- `tests/live/upstream_audit_via_proxy.py dd|law` runs an upstream's validation
  audit script through this proxy (needs the sibling repos checked out).
- Releases: the `/release` skill (`.claude/skills/release/SKILL.md`) — one
  approval gate at `gh release create`, one repo at a time, rollback stated
  first, proxy live checks before and after.
